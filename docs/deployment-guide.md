# Deployment guide: Access seat-equivalent allocation evidence

This guide explains how to deploy this repository into any Cloudflare account that uses Cloudflare Access and wants to visualize observed user-to-application usage from `access_requests` logs.

The deployed architecture is:

```text
Access access_requests Logpush -> R2 -> scheduled Workflow -> D1 -> Access-protected Viewer Worker
```

The viewer provides:

- team-level seat-equivalent allocation evidence
- user-to-application relationship CSV export
- Workflow run status
- manual Access app owner assignment for users in `MAIN_ADMIN_EMAILS`

The tool produces evidence for Finance or platform teams. It does not determine contractual billable seats or reconcile invoices.

## 1. Prerequisites

### Local tooling

Install dependencies from the repository root:

```bash
npm install
```

Authenticate Wrangler to the target Cloudflare account:

```bash
npx wrangler login
npx wrangler whoami
```

Use an API token or user session with permissions for:

- Workers Scripts Write
- Workflows Write
- D1 Write
- R2 Read or Admin for the log bucket binding
- Logpush Write if you need to create the Logpush job
- Access Apps and Policies Write if you want to create the viewer Access app

### Cloudflare account prerequisites

You need:

1. A Cloudflare account ID.
2. An R2 bucket for Access Logpush output.
3. A Logpush job for the account-level `access_requests` dataset writing to that bucket.
4. A D1 database for the reporting data.
5. A Worker route or `workers.dev` hostname for the viewer.
6. A Cloudflare Access application protecting the viewer.

## 2. Clone and prepare the repo

```bash
git clone <repository-url>
cd zt-access-seat-chargeback
npm install
npm test
npm run typecheck
```

## 3. Configure Logpush to R2

If the account already has an `access_requests` Logpush job to R2, record:

- bucket name
- destination prefix, if any
- whether `{DATE}` is used in the destination path

This implementation expects Logpush daily folders where `{DATE}` resolves to `YYYYMMDD`, for example:

```text
20261104/20261104T111726Z_20261104T111726Z_<suffix>.log.gz
```

If your destination path has a parent prefix, for example `access/{DATE}`, set:

```jsonc
"LOG_PREFIX": "access"
```

If you need to create a Logpush job, configure an account-level Logpush job with an R2 destination that includes `{DATE}` in the object path. Create R2 credentials in the target account and keep those credentials out of source control.

Dataset:

```text
access_requests
```

Required fields for this app:

- `Action`
- `Allowed`
- `AppDomain`
- `AppUUID`
- `CreatedAt`
- `Email`
- `RayID`
- `UserUID`

The Worker filters to `Allowed = true`, `Action = login`, `UserUID` present, and `AppUUID` present.

## 4. Create the D1 database

Create a D1 database in the target account:

```bash
npx wrangler d1 create zt-access-seat-chargeback
```

Copy the returned `database_id` into `wrangler.jsonc`:

```jsonc
"d1_databases": [
  {
    "binding": "DB",
    "database_name": "zt-access-seat-chargeback",
    "database_id": "<database_id>",
    "migrations_dir": "migrations"
  }
]
```

Keep account-specific IDs out of generic commits when this repository is shared across accounts. Prefer an environment-specific Wrangler config, a deployment branch, or CI/CD variables if multiple accounts will deploy the same code.

## 5. Configure `wrangler.jsonc`

Update these values before deployment.

### Worker name

```jsonc
"name": "zt-access-seat-chargeback"
```

Use a unique Worker name if you deploy multiple copies.

### Variables

```jsonc
"vars": {
  "ACCOUNT_ID": "<account_id>",
  "LOOKBACK_DAYS": "3",
  "BATCH_SIZE": "100",
  "MAX_PAGES_PER_RUN": "10",
  "LOG_PREFIX": "",
  "OWNER_TAG_KEY": "owner_team",
  "EXCLUDED_APP_UUIDS": "",
  "ADMIN_EMAILS": "admin1@example.com,admin2@example.com",
  "MAIN_ADMIN_EMAILS": "owner-admin@example.com",
  "SESSION_ASSUMPTION": "24h",
  "METHOD_VERSION": "access-logins-v1"
}
```

Guidance:

- `ACCOUNT_ID`: target Cloudflare account ID.
- `LOOKBACK_DAYS`: rolling lookback window for late Logpush files.
- `BATCH_SIZE`: R2 objects listed per Workflow page.
- `MAX_PAGES_PER_RUN`: cap to avoid unbounded Workflow runs.
- `LOG_PREFIX`: parent prefix before `{DATE}`, if any.
- `OWNER_TAG_KEY`: Resource Tagging key used for app owner team.
- `EXCLUDED_APP_UUIDS`: comma-separated Access app UUIDs to exclude, such as the viewer app itself.
- `ADMIN_EMAILS`: users allowed to view the dashboard. If empty, Access policy is the only viewer gate.
- `MAIN_ADMIN_EMAILS`: users allowed to write manual app owner mappings. Keep this narrow.

### R2 binding

```jsonc
"r2_buckets": [
  {
    "binding": "LOG_BUCKET",
    "bucket_name": "replace-with-logpush-r2-bucket"
  }
]
```

### Workflow schedule

The default scheduled Workflow runs daily at 02:00 UTC:

```jsonc
"workflows": [
  {
    "name": "zt-access-seat-chargeback-ingest",
    "binding": "INGEST_WORKFLOW",
    "class_name": "IngestWorkflow",
    "schedules": ["0 2 * * *"]
  }
]
```

Change the cron expression if the account needs a different ingestion time.

## 6. Apply D1 migrations

After adding the D1 `database_id`, apply migrations remotely:

```bash
npx wrangler d1 migrations apply DB --remote
```

Verify the expected tables exist:

```bash
npx wrangler d1 execute DB --remote --command "SELECT name FROM sqlite_master WHERE type='table' ORDER BY name;"
```

Expected application tables include:

- `access_events`
- `app_owner_override`
- `app_owner_snapshot`
- `processed_files`
- `report_export_files`
- `report_exports`
- `run_state`
- `usage`
- `users`
- `workflow_runs`

## 7. Deploy Worker and Workflow

Validate the bundle first:

```bash
npm test
npm run typecheck
npx wrangler deploy --dry-run
```

Deploy:

```bash
npx wrangler deploy
```

The deploy should show bindings for:

- `INGEST_WORKFLOW`
- `DB`
- `LOG_BUCKET`
- environment variables from `vars`

## 8. Protect the viewer with Cloudflare Access

Create a Cloudflare Access self-hosted application for the Worker hostname.

If using `workers.dev`, the hostname normally looks like:

```text
<worker-name>.<workers-subdomain>.workers.dev
```

Access app settings:

- Application type: Self-hosted
- Domain: Worker hostname
- Session duration: align with `SESSION_ASSUMPTION`, default `24h`
- Policy: allow only the finance/platform users who should view the dashboard

Important:

- `ADMIN_EMAILS` is an app-level allowlist inside the Worker.
- `MAIN_ADMIN_EMAILS` is the write allowlist for manual owner mappings.
- The Access policy should still be the primary perimeter control.

## 9. Configure ownership mapping

The app supports two ownership sources.

### Option A: manual owner assignment in the viewer

Users in `MAIN_ADMIN_EMAILS` can assign owner teams from the viewer's unassigned-apps table. This writes:

- `app_owner_override`
- the current period's `app_owner_snapshot`

API equivalent:

```bash
curl -X POST https://<worker-host>/api/app-owner \
  -H 'content-type: application/json' \
  -d '{
    "period": "YYYY-MM",
    "app_uuid": "<access-app-uuid>",
    "owner_team": "security-platform",
    "cost_center": "optional",
    "reason": "manual owner assignment"
  }'
```

### Option B: Resource Tagging sync

The code includes a Resource Tagging path, but deployments should validate the exact account API permissions and Access application resource type before relying on it.

If enabled in a later iteration, store API credentials as a secret, never in `wrangler.jsonc`:

```bash
npx wrangler secret put CLOUDFLARE_API_TOKEN
```

The token should be least-privilege and only able to read Access applications and Resource Tags.

## 10. Smoke test ingestion

Trigger a small manual Workflow run:

```bash
curl -X POST https://<worker-host>/api/ingest \
  -H 'content-type: application/json' \
  -d '{"lookbackDays":1,"batchSize":10,"reason":"manual-smoke-test"}'
```

Check run state:

```bash
curl https://<worker-host>/api/runs
```

Or query D1:

```bash
npx wrangler d1 execute DB --remote --command "SELECT * FROM workflow_runs ORDER BY started_at DESC LIMIT 5;"
npx wrangler d1 execute DB --remote --command "SELECT COUNT(*) AS processed_files FROM processed_files;"
npx wrangler d1 execute DB --remote --command "SELECT COUNT(*) AS usage_rows FROM usage;"
```

If `files_seen = 0` but the bucket has files, check:

- `LOG_PREFIX`
- `{DATE}` folder format
- R2 bucket binding name
- whether the Logpush job is writing to the same bucket

## 11. Viewer and export checks

Open the viewer:

```text
https://<worker-host>/
```

Check these endpoints:

- `/api/health`
- `/api/runs`
- `/api/allocation?period=YYYY-MM`
- `/api/allocation.csv?period=YYYY-MM`
- `/api/relationships.csv?period=YYYY-MM`
- `/api/app-owners`

Expected behavior:

- Unauthenticated users are redirected to Access.
- Users not in `ADMIN_EMAILS`, when configured, receive 403.
- Users not in `MAIN_ADMIN_EMAILS` cannot write `/api/app-owner`.
- Allocation rows show `unassigned` until ownership mappings exist.

## 12. Operational settings

Suggested starting values:

```jsonc
"LOOKBACK_DAYS": "3",
"BATCH_SIZE": "100",
"MAX_PAGES_PER_RUN": "10"
```

Increase `BATCH_SIZE` or `MAX_PAGES_PER_RUN` only after checking Worker and Workflow duration. The design intentionally uses bounded R2 listing so a large R2 prefix does not require one unbounded Worker invocation.

For month close:

1. Wait for the configured late-file lag, default 3 days.
2. Trigger or wait for ingestion over the lookback window.
3. Review unassigned apps.
4. Add owner overrides or Resource Tags.
5. Export team totals and relationship CSVs.
6. Keep the export context for auditability.

## 13. Troubleshooting

### `Download relationship CSV` returns a Worker exception

Check the deployed version includes the qualified relationship query. The correct ordering is:

```sql
ORDER BY owner_team, u.app_domain, users.email
```

If an older Worker is deployed, redeploy from the current `main` branch.

### No R2 files are processed

Check:

- the Logpush job is enabled
- the bucket in `wrangler.jsonc` matches the Logpush destination
- `LOG_PREFIX` matches the destination prefix before `{DATE}`
- daily folder format is `YYYYMMDD`
- the Worker has the `LOG_BUCKET` R2 binding

### All apps are `unassigned`

This is expected until ownership mappings exist. Use the viewer manual assignment UI or insert rows into `app_owner_override`.

### Viewer loads but write forms do not appear

Confirm the signed-in user's email is in `MAIN_ADMIN_EMAILS`. `ADMIN_EMAILS` alone grants view access, not write access.

### Direct `curl` returns 302

That is expected when Access protects the viewer. Test through a browser session authenticated by Access, or use Access service-token based automation if appropriate.

## 14. Production hardening checklist

Before using for a real chargeback or Finance process:

- Confirm privacy approval for user-to-application reporting.
- Confirm session duration assumptions for all in-scope Access apps.
- Decide retention for D1 rows and raw R2 logs.
- Exclude the viewer app and other admin apps via `EXCLUDED_APP_UUIDS`.
- Restrict `MAIN_ADMIN_EMAILS` to a small owner/admin group.
- Verify monthly exports with Finance before using them for allocation.
- Confirm Resource Tagging or manual override ownership coverage before month close.
